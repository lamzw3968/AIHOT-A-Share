# 专业代理共同工作规则

本文件是三个专业角色共用的工作协议，由主代理维护。每次任务先读取当前 `AGENTS.md`、`README.md`、本文件、`known-state.md`，再读职责相关文档和源码。遵守当前会话指令及授权；历史记录不构成授权。

## 任务分派与文件归属

主代理 AIHOT Project Orchestrator 负责任务拆分、依赖、权限、文件归属和最终汇总。每次委派提供：

```text
目标与验收标准：
专业角色：
执行模式：只读分析 / 方案 / 已授权修改
目标环境与项目根目录：
可修改文件或明确目录范围：
前置依赖与已核实证据：
应运行的验证：
已获授权的外部调用或生产操作范围：
不在授权内的操作及返回主代理的条件：
```

- 只有主代理分派的任务才执行；加载角色不自动开始业务改造、采集、重评或部署。
- 写入范围以任务分派为准，不因角色提到某目录就获得整个目录的任意修改权。finance 的行业范围不包含自行改变用户选定的信源；信源配置由 source 负责，服务和基础设施由 ops 负责。
- 主代理维护本次任务的文件归属清单，同一文件只分配一个写入者，包括测试和文档。完成差异检查并交接后，下一代理才可写；不能用相同工作区的并行代理抢写。
- 可并行读取和检查不相交的子任务；共用数据库的集成测试串行执行，避免相互清理数据。另开 worktree 也不代表允许未经协调合并同一文件。
- 范围扩大、发现跨领域根因或需要高风险操作时，提交证据、相关文件、最小建议、风险和兼容影响，由主代理协调；有现成授权不重复向用户索要相同确认。
- 子代理向主代理返回结果，由主代理统一面向用户解释；不擅自发外部消息、工单、通知或触发上线。

## 查证与架构

- 修改前先 `git status`、确认 branch/HEAD 和已有差异。用 `rg`/`rg --files` 优先搜索；先读源码，区分代码、配置、数据、运行故障，再提出最小改动。每个结论给出证据，标明推断和未验证项。
- 路径根据当前 checkout/worktree 和目标环境发现，不依赖创建时的 Windows 路径或历史服务器路径；先确认文件存在，不猜源码路径或 Source 字段。
- 前端只经 HTTP 读 API；公开出口共用 publication；模型只在 worker 的任务调用；付费请求走回执和预算。不绕开安全阀、认证、参与方式、发布时间和历史回灌规则。
- 公共内容匿名一致，后台仅管理员。信源默认摘要与原文链接，`site_fulltext`/`syndicate_fulltext` 只有明确授权才开放。技术上可抓取不等于有全文展示许可。
- 财经定制优先在行业层；改其他层先说明必要性、影响和上游兼容性。保留通用模块，通过 Feature 关闭 AI 专属功能，不随手删代码。
- 站名、信源、分类、重要性/噪声及条款隐私先查用户已确认决定；没有决定才问，不自行编造运营信息。

## 生产授权、数据与凭据

- 默认只读生产检查。主代理核对用户是否已授权部署、生产数据写入、历史重评、秘密配置修改、数据库 schema、API 协议或核心队列变更，再分派具体范围；普通开发授权不自动覆盖这些操作。
- 未明确批准具体对象和操作时，禁止 DROP/TRUNCATE、删除大量生产 articles/analyses/publications/receipts、删除数据库 volume、`docker compose down -v`、强推和 hard reset。不得以“重跑”“修复”或“重新部署”为理由清库。
- 生产 UPDATE 或批量操作前先 SELECT 确认对象、筛选条件和数量，给主代理具体 SQL/命令、影响、备份/恢复及验证办法。等待授权核对后执行，不越过已有授权范围。
- 迁移仅可向后兼容增量追加，不能修改已应用迁移或擅自改变 schema。保留旧分析和回执；新的 Prompt 哈希不等于已触发历史重评。
- 不读取或输出真实 `.env`、Key、密码、Cookie/token、session secret、ingest token；凭据状态只检查存在、长度和配置。使用已配置的认证通道不需要把秘密带入聊天或文件。禁止未经脱敏打印完整环境、连接串、HTTP headers、Compose 展开结果或日志。
- 开发和测试明确设置 `COLLECT_ENABLED=false`、`MODEL_CALLS_ENABLED=false`、`FEISHU_CONTENT_PUSH_ENABLED=false`、`FEISHU_INTERNAL_ENABLED=false`、`INDEXNOW_SUBMIT_ENABLED=false`；源码默认值不能当作关闭。测试服务仅用本地固定样本/假 Provider。
- 真实采集、模型验证和 Gold Set 评测按主代理明确任务及费用范围执行，仍经过原回执预算；unknown receipt 可能已计费，先查恢复机制，不直接重发。

## Git 与验证

- 保留用户和其他代理已存在的修改，逐任务控制差异，修改后检查 `git diff`。不擅自 commit/push、清理文件、切换会丢失修改的状态或更改全局 Codex 配置。
- 应用验证按根 AGENTS 和涉及的重要行为执行。行业改动运行 typecheck、迁移独立空测试库后 npm test、Web build/tests；测试站已运行时 smoke。测试库名必须以 `_test` 或 `_ci` 结尾，绝不连接生产库代替。
- AI 示例 fixture 可换财经等价样本，不能删测试、skip、降低断言或掩盖错误。缺依赖/测试库等条件时报告未运行、原因及补齐方式，不能声称通过。
- 仅代理配置/文档变更检查 TOML 必需字段、内部引用、职责路由、文件范围和差异，不为验证配置启动业务或联网模型调用。
- 上线任务由 ops 交付构建/部署/恢复方案，主代理核对已有用户授权后再委派执行。行业 TypeScript/Prompt 通常进镜像，先读 Dockerfile 判断 rebuild；检查 setup 的迁移与 seed 副作用。

每次子代理完成任务向主代理报告以下内容。无修改、无测试或无影响也要明确填写，不只写 done/fixed/completed。

```text
任务目标：
根因/结论（证据与推断分开）：
检查过的关键文件：
实际修改文件：
修改原因与设计决定：
测试/验证结果（含未运行项及原因）：
数据库影响：
生产环境影响：
是否需要 rebuild：
是否需要重新分析历史文章：
剩余风险：
下一步建议：
需主代理协调/核对授权的事项：
```

## 长期维护

根 AGENTS 维护路由和项目原则；各 TOML 维护专用职责；本文件维护共用协议；known-state 维护带来源与时间的背景。不要维护互相矛盾的规则副本。用户授权的新长期决定及时更新对应文档；历史观测在现场复核前不升级为当前事实。持久化的是这些文件，不是所有会话记忆或常驻 Agent 进程。
